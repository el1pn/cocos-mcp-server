# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Cocos Creator 3.8+ editor extension that runs an MCP (Model Context Protocol) server inside the editor's main process, exposing scene/node/component/prefab/asset control to AI clients (Claude Code, Cursor, VS Code, etc.) over HTTP.

## Commands

```bash
npm run build          # tsc build, source/ -> dist/
npm run watch          # tsc -w, rebuild on save
npm run audit:messages # lint every Editor.Message.request(...) call against scripts/cocos-messages.json
npm run build:cocos-inventory  # regenerate scripts/cocos-messages.json from a Cocos app path
```

There is no test framework (no jest/mocha). Tests are plain Node scripts using `assert`, run directly:

```bash
node source/test/mcp-clients-write.test.ts   # needs a prior tsc build, or run via ts-node if available
node source/test/protocol-compliance.check.js  # asserts against compiled dist/mcp-server.js — run after npm run build
```

This extension only runs loaded inside a Cocos Creator editor instance (`main.ts` load/unload hooks, `Editor.*` APIs) — there is no standalone way to run the server outside the editor. To exercise changes, install into a Cocos project's `extensions/` folder (see README.md), rebuild, restart the editor, and use the panel's **Start Server** / **Tester** tab, or connect a real MCP client to `http://127.0.0.1:3000/mcp`.

When working on this repo *through* the `cocos-creator-3x` MCP tools (i.e. using this server's own tools to inspect a live editor), see the MCP server instructions block for the tool-usage contract (inspect before modifying, use tools not direct file edits for scene/prefab structural changes, `batch_execute` for multi-step calls, etc.).

## Architecture

Full diagram and request-flow: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Key points a change usually touches:

**Two processes, one extension.** `main.ts` runs in the editor's main process (load/unload, panel IPC). `mcp-server.ts` (also main process) runs the HTTP/JSON-RPC server. `scene.ts` is a *separate* scene script that runs in the renderer process — it's the only place with access to `cc.director`/`cc.Node` at runtime, invoked via `Editor.Message.request('scene', 'execute-scene-script', ...)`. When a tool needs to touch live scene objects (not just editor/asset-db state), the call has to cross this boundary into `scene.ts`.

**Action-based tool consolidation.** There is no one-tool-per-operation design. Each file in `source/tools/` implements one `ToolExecutor` (`getTools(): ToolDefinition[]` + `execute(toolName, args)`) that owns one MCP tool name (e.g. `node_lifecycle`) and dispatches internally on an `action` string enum (`create`, `delete`, `duplicate`, ...). When adding a new operation, prefer adding an action to an existing tool over registering a new tool name — this is deliberate (fewer tools = fewer tokens in `tools/list`, higher call accuracy from the LLM client). New tool files get instantiated in `MCPServer.initializeTools()` and wired in `setupTools()` in `mcp-server.ts`.

**`normalizeToolArguments()`** in `mcp-server.ts` silently corrects common LLM parameter mistakes (`operation`/`command` → `action`, `node_uuid` → `nodeUuid`, `remove`/`destroy` → `delete`, etc.) before dispatch. If you see a tool receiving oddly-named args, check here first before assuming the client is broken.

**Asset writes go through `AssetSafety.safeCreateAsset()`** (`source/utils/asset-safety.ts`): ensure parent dirs → create-asset → optional meta modification → refresh-asset. Don't write assets by calling `asset-db` messages directly in new tool code; use this pipeline so partial failures don't leave the asset DB out of sync.

**Texture→SpriteFrame resolution** (`source/utils/asset-utils.ts`, `resolveSpriteFrameUuid`) auto-corrects the common case of an LLM passing a Texture2D UUID where a SpriteFrame sub-asset UUID is required. Already hooked into `component-tools.ts` for `spriteFrame`-typed properties — reuse it for any new component property of that type rather than re-deriving the UUID.

**Editor message inventory.** `scripts/cocos-messages.json` is the allow-list of legitimate `Editor.Message.request/send/broadcast('<ext>', '<msg>', ...)` calls, generated by `scripts/build-cocos-inventory.js` from a real Cocos editor install. `npm run audit:messages` greps `source/**/*.ts` for such calls and fails if one isn't in the inventory (own extension name and a small manual allow-list in the script are exempted). If you add a new `Editor.Message` call to an unfamiliar built-in extension/message pair, either regenerate the inventory against a Cocos install or add a justified entry to `ALLOWED_UNDECLARED` in `scripts/audit-messages.js`.

**Transport.** Direct HTTP (`POST /mcp`) for most clients; `mcp-proxy.ts` is a separate stdio↔HTTP bridge process for stdio-only clients (Claude Desktop) — it has no protocol logic of its own, just forwards. `mcp-clients.ts` handles auto-registering this server into client config files (e.g. `~/.claude.json`) once a project path is detected there.

**i18n.** UI-facing strings (panel labels, package.json `i18n:` keys) resolve from `i18n/en.js` / `i18n/zh.js`. Tool descriptions/schemas sent to MCP clients are plain English in the tool source files, not i18n'd.

## Conventions specific to this repo

- `dist/` is committed (built output tracked in git) — after editing `source/`, run `npm run build` so `dist/` stays in sync before committing, since the extension actually loads from `dist/` (`package.json` `main` and `panels`/`scene` contribution paths all point at `dist/`).
- Tool schemas favor short descriptions (see commit history: "trim verbose tool schema descriptions to reduce token overhead") — don't restore verbose multi-line descriptions on tool parameters.
- `source/types/index.ts` holds all shared interfaces; check there before adding a duplicate type.
